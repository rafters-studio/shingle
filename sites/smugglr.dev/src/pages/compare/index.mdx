<div class="font-heading font-medium text-sm uppercase tracking-widest text-muted-foreground mb-3.5 pt-3.5 border-t border-foreground">01 &middot; the lay of the land</div>
<H2>You are not building a database. You are moving rows between places that already have one.</H2>

<P size="display-small">SQLite is everywhere already. The phone has it. The laptop has it. Cloudflare D1 is it. Turso is it. Datasette and rqlite and StarbaseDB run on it. The hard part of "local-first" or "multi-device" or "edge-distributed" is not picking a database; it is keeping every node holding the same rows.</P>

<P size="display-small">smugglr is one tool that does that one job. SQLite on every node. Content-hash diff between them. Run it as a CLI, embed it as a Rust crate, install the npm package in the browser or Node. No central server. No managed cloud. No per-row pricing.</P>

<P size="display-small" color="muted-foreground">The matrix below names every comparable tool and what it actually solves. Building a multiplayer game? <a href="/compare/games/" class="underline decoration-border underline-offset-4 hover:decoration-foreground transition-colors">/compare/games/</a> is the games-shaped read.</P>

<div class="font-heading font-medium text-sm uppercase tracking-widest text-muted-foreground mb-3.5 pt-3.5 border-t border-foreground">02 &middot; sync engine peers</div>
<H2>The closest neighbors. SQLite-shaped, row-shaped, on the same shelf.</H2>

<P size="display-small">Six tools sit nearest smugglr. None do exactly what it does. The differences are operational, not philosophical.</P>

<Grid columns={2} gap="6">
    <Card>
        <CardHeader>
            <CardTitle>Litestream</CardTitle>
            <CardDescription>SQLite to S3. One way. Backup-shaped.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>Litestream streams a SQLite WAL to S3. One source, many readers. It does not move rows between two live SQLite databases on different machines. smugglr does. Litestream answers "back this up to S3 continuously." smugglr answers "keep all my SQLite copies the same."</P>
        </CardContent>
    </Card>

    <Card>
        <CardHeader>
            <CardTitle>rqlite, dqlite</CardTitle>
            <CardDescription>Raft-clustered SQLite. The cluster is the database.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>Every node is a peer in a coordinated quorum. You operate a cluster. smugglr does not run a cluster; it moves rows between SQLite files that already exist. Pick rqlite if you want linearizable writes across nodes; pick smugglr if you want each node to own its own SQLite file and reconcile on a schedule.</P>
        </CardContent>
    </Card>

    <Card>
        <CardHeader>
            <CardTitle>ElectricSQL, PowerSync</CardTitle>
            <CardDescription>Postgres on the server, SQLite on the client, sync service in the middle.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>Both assume an authoritative Postgres backend and a sync service that runs in front of it. The model is one server, many local replicas. Conflict resolution is the service's job. smugglr does not assume an authoritative server. Every node is peer-symmetric. If you already run Postgres and want SQLite on your clients, ElectricSQL or PowerSync are the right tools. If you want SQLite end to end, smugglr is the right tool.</P>
        </CardContent>
    </Card>

    <Card>
        <CardHeader>
            <CardTitle>Turso embedded replicas</CardTitle>
            <CardDescription>Hosted libSQL with read replicas pulled to the client.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>Turso runs the authoritative database. Replicas are read-only on the client; writes go back to Turso. smugglr ships a Turso target, so smugglr writes into Turso the same way it writes into a local file. Turso embedded replicas tie you to Turso. smugglr ties you to SQLite. Both are fine choices; the question is whether you want a vendor or a file format.</P>
        </CardContent>
    </Card>

    <Card>
        <CardHeader>
            <CardTitle>CR-SQLite</CardTitle>
            <CardDescription>CRDT extension to SQLite. Concurrent writes merge by construction.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>The cost is the table model: every column gets versioned metadata, schema migrations are heavier, the merge semantics are the ones CRDTs offer. smugglr is the opposite trade. Plain SQLite tables. Last-received-wins on divergence. UUIDv7 primary keys to avoid collisions in the first place. CR-SQLite is the right call when divergent concurrent writes on the same row are common; smugglr is the right call when they are rare.</P>
        </CardContent>
    </Card>

    <Card>
        <CardHeader>
            <CardTitle>Syncthing on a .sqlite file</CardTitle>
            <CardDescription>Filesystem sync. Works until two nodes write at once.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>Filesystem sync of a SQLite file works until two nodes write at once. Then the file is corrupt, not merged. smugglr operates at the row level using content hashes, so concurrent writes on different tables or different rows reconcile cleanly. If you tried Syncthing for SQLite and got a corrupted database, that is the reason.</P>
        </CardContent>
    </Card>
</Grid>

<div class="font-heading font-medium text-sm uppercase tracking-widest text-muted-foreground mb-3.5 pt-3.5 border-t border-foreground">03 &middot; hosted services that solve part of the same problem</div>
<H2>The shortcut option. Pay per operation, accept the lock-in, ship faster.</H2>

<P size="display-small">These services are real shortcuts to "users see fresh data on every device." They cost money per row and they own the schema. smugglr is the slower-to-set-up, cheaper-at-scale, lock-in-free alternative.</P>

<Grid columns={2} gap="6">
    <Card background="muted">
        <CardHeader>
            <CardTitle>Firebase Realtime DB, Firestore</CardTitle>
            <CardDescription>Hosted JSON tree or document store with realtime fan-out.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>The fastest way to ship a multi-device app, until the bill arrives. Free Spark tier is generous; Blaze prices reads, writes, and storage individually. Costs scale non-linearly with a real workload. Lock-in is real: data lives in Google's schema, security rules are theirs, exports are work. smugglr does not host data. SQLite is the data. Migration cost off smugglr is choosing a different SQLite client; migration off Firebase is rewriting the data layer.</P>
        </CardContent>
    </Card>

    <Card background="muted">
        <CardHeader>
            <CardTitle>Supabase Realtime</CardTitle>
            <CardDescription>Postgres logical replication, broadcast over a websocket.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>The closest tool to "realtime that does not need C++." Real value when you already run Supabase Postgres. The cost is operational complexity: websockets behind a CDN, message-rate limits, connection ceiling. Teams hit those ceilings and drop it when the loop does not actually require sub-second push. If your loop is per-action rather than per-frame, smugglr's <Code>watch</Code> daemon and LAN broadcast cover the same shape without a websocket layer or a Supabase project.</P>
        </CardContent>
    </Card>

    <Card background="muted">
        <CardHeader>
            <CardTitle>Convex</CardTitle>
            <CardDescription>Hosted reactive backend. Functions, queries, and live data in one platform.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>Convex bundles a database, a function runtime, and a reactive client into one product. Lock-in is total: data, schema, query language, and runtime are theirs. The free tier is enough to evaluate; paid usage is per-operation. Convex is the right call if you want one vendor for the whole reactive backend and you accept the lock-in. smugglr is the right call if you want SQLite on every node and the freedom to host the rest of the stack yourself.</P>
        </CardContent>
    </Card>

    <Card background="muted">
        <CardHeader>
            <CardTitle>MongoDB Atlas Device Sync</CardTitle>
            <CardDescription>Realm on the client, MongoDB Atlas on the server, sync between them.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>The mobile-first incumbent. Realm is a real local database with reactive queries; Atlas is the cloud counterpart. Sync is bidirectional with Realm-defined conflict resolution. The cost is the document model and the per-MAU pricing on Atlas. smugglr is relational and free-as-in-MIT, with SQLite as the local store and your hosting as the server. If you need Realm's mobile reactivity primitives, Atlas Device Sync is the fit; if you want SQLite, smugglr is the fit.</P>
        </CardContent>
    </Card>
</Grid>

<div class="font-heading font-medium text-sm uppercase tracking-widest text-muted-foreground mb-3.5 pt-3.5 border-t border-foreground">04 &middot; the client-cache layer</div>
<H2>Reactive caches with mutators. Different shape from sync engines, often confused.</H2>

<P size="display-small">These libraries solve the front-end half of local-first: optimistic UI, reactive queries, mutator functions. They sync against a backend you operate. smugglr does not ship a reactive cache, but the npm adapters bridge to the most common ones.</P>

<Grid columns={2} gap="6">
    <Card background="muted">
        <CardHeader>
            <CardTitle>Replicache, Zero</CardTitle>
            <CardDescription>Client-side reactive cache plus push, pull, and poke against your backend.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>You implement push and pull endpoints; the library handles the cache, the optimistic UI, and the reconciliation. The model is client to server, not peer to peer. smugglr does not ship a reactive cache. If you already use Zustand or Nanostores, the <Code>@smugglr/zustand</Code> and <Code>@smugglr/nanostores</Code> adapters persist your existing store to a local SQLite table and rehydrate it on every sync. Pick Replicache or Zero for their cache and mutator model; pick smugglr if you have a state store and want sync without rewriting the cache layer.</P>
        </CardContent>
    </Card>

    <Card background="muted">
        <CardHeader>
            <CardTitle>Yjs, Automerge</CardTitle>
            <CardDescription>CRDT primitives for collaborative documents. Peer-to-peer or relay.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>If your data is a document with concurrent edits at the character level, these are the right tools. Yjs powers Liveblocks, TipTap collab, and most production collaborative editors. Automerge ships JSON-CRDT primitives. smugglr is row-shaped, not character-shaped; concurrent writes on the same row resolve by last-received-wins, not by merge. Pick Yjs or Automerge for documents; pick smugglr for relational state.</P>
        </CardContent>
    </Card>

    <Card background="muted">
        <CardHeader>
            <CardTitle>RxDB, WatermelonDB</CardTitle>
            <CardDescription>Local-first reactive databases for the browser and React Native.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>Both ship a local store with reactive queries and pluggable sync backends. RxDB is JSON, WatermelonDB is SQLite-backed and React Native-shaped. They overlap with smugglr on the local-first claim and differ on the sync layer: RxDB and WatermelonDB ask you to bring or build a sync server; smugglr is the sync, and you bring the client. The npm package + state-store adapters cover the same use case in a thinner stack.</P>
        </CardContent>
    </Card>

    <Card background="muted">
        <CardHeader>
            <CardTitle>Liveblocks, Yjs providers</CardTitle>
            <CardDescription>Hosted CRDT relays with presence, history, and webhooks.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>Liveblocks is the managed-Yjs option: hosted relay, presence channels, comments, version history, webhooks. Per-MAU pricing. The right call when you are shipping collaborative document UX and do not want to operate the relay. smugglr is not in that lane; pair Liveblocks with smugglr if your app has collaborative documents (Liveblocks) and relational app state (smugglr) as separate concerns.</P>
        </CardContent>
    </Card>
</Grid>

<div class="font-heading font-medium text-sm uppercase tracking-widest text-muted-foreground mb-3.5 pt-3.5 border-t border-foreground">05 &middot; four shapes that fit smugglr</div>
<H2>Concrete jobs, named so you can recognize yours.</H2>

<Grid columns={2} gap="6">
    <Card>
        <CardHeader>
            <CardTitle>Dev, staging, prod, CI hold the same rows</CardTitle>
            <CardDescription>The original use case. The reason this binary exists.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>Your local dev box, your CI runner, your staging environment, and prod all want the same SQLite file kept in sync, sometimes one-way, sometimes bidirectional. smugglr handles the diff and the write with typed exit codes for the agents and pipelines that orchestrate it.</P>
        </CardContent>
    </Card>

    <Card>
        <CardHeader>
            <CardTitle>One app on phone, web, and desktop</CardTitle>
            <CardDescription>Local-first SaaS. Notes, knowledge bases, task managers, journals.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>The user expects every device to show the same data. The default answer is Firestore or Supabase; both meter you per row and own the schema. smugglr is the alternative: SQLite on every device, sync over the network you already have, no per-MAU bill, no vendor lock.</P>
        </CardContent>
    </Card>

    <Card>
        <CardHeader>
            <CardTitle>Edge replicas next to your users</CardTitle>
            <CardDescription>Read-fast deployments without the data tier becoming the bottleneck.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>You run Cloudflare Workers, Fly Machines, or regional VMs and want a local SQLite next to the application. smugglr ships into D1, Turso, rqlite, Datasette, StarbaseDB, and SQLite Cloud, so the same engine that syncs your laptop to staging syncs your origin to every region.</P>
        </CardContent>
    </Card>

    <Card>
        <CardHeader>
            <CardTitle>Agent memory that survives sessions</CardTitle>
            <CardDescription>Coordinated state across machines, processes, and agent invocations.</CardDescription>
        </CardHeader>
        <CardContent>
            <P>An AI agent running on multiple boxes wants a shared SQLite for memory, decisions, and audit trail. smugglr ships JSON output, typed exit codes, and a watch daemon, so an agent can sync its own memory without parsing prose. Same engine, agent-shaped invocation.</P>
        </CardContent>
    </Card>
