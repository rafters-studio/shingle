Nine scenarios. Every config block below is a file under `docs/examples/` in the smugglr repository, named where it is used. Every output block is stdout from smugglr 0.5.0 run against the Westwind sample in `docs/examples/westwind/` (forty customers, three hundred and twenty orders, seven hundred and eighty-eight order lines), copied from that example's README or captured on 2026-08-28. Text mode also writes timestamped `INFO` lines to stderr; a section says so where stderr is what it shows. The summary block lists tables in map order, so two runs print the same counts in a different order. Compare counts, not line positions.

Two install facts apply to every pattern with a remote target. `cargo install smugglr` and the curl installer give the CLI. Any target other than a local SQLite file is reached through a second binary, `smugglr-http-sql` (`cargo install smugglr-http-sql`, or the release archive from 0.5.1, which carries both). D1 is one profile of that plugin, and in 0.5.0 it cannot be reached: the core hands the plugin the wrong keys (smugglr#429), the plugin does not ship with the CLI (smugglr#430), and the d1 profile misreads its rows (smugglr#436). Where a pattern below names D1, the runnable form is a second SQLite file or the `type = "plugin"` shape, and the D1 variant waits on those three issues.

## 1. Local to Cloud

Push a local SQLite database, one direction, to a target you treat as a copy.

### When to use

You have a local database (your dev environment, a seed, a migration result) and one target that should match it. You are the source of truth. The runnable form is `docs/examples/cli-sqlite-to-sqlite`: two SQLite files on one machine, no credentials, no plugin. The same diff engine and the same summary block run against every hosted backend, and the D1 variant of this pattern waits on smugglr#429, #430, and #436.

### Config

`docs/examples/cli-sqlite-to-sqlite/config.example.toml`, comments removed:

```toml
local_db = "./local.db"

[target]
type = "sqlite"
database = "./backup.db"

[sync]
tables = []
timestamp_column = "updated_at"
conflict_resolution = "local_wins"
```

Build both files from the sample: `../westwind/make.sh ./local.db` and `../westwind/make.sh --empty ./backup.db`. smugglr moves rows, not DDL, so the target must already carry the tables.

### Commands

A dry-run reads both sides, hashes every row, and reports what a push would write. From the example README:

```
$ smugglr push --dry-run
--- Push Summary ---
  order_details: 788 rows
  suppliers: 8 rows
  employees: 9 rows
  shippers: 3 rows
  categories: 8 rows
  products: 20 rows
  customers: 40 rows
  orders: 320 rows

  (dry run - no actual changes made)
```

The push writes what the dry-run described. Same counts, minus the dry-run line:

```
$ smugglr push
--- Push Summary ---
  suppliers: 8 rows
  products: 20 rows
  employees: 9 rows
  customers: 40 rows
  order_details: 788 rows
  categories: 8 rows
  orders: 320 rows
  shippers: 3 rows
```

One table, with `--table`. Captured against a fresh pair, before the full push:

```
$ smugglr push --dry-run --table customers

--- Push Summary ---
  customers: 40 rows

  (dry run - no actual changes made)
```

```
$ smugglr push --table customers

--- Push Summary ---
  customers: 40 rows
```

A second push has nothing to move, because every content hash now matches. From the example README:

```
$ smugglr push

--- Push Summary ---
  No changes to push
```

### Watch for

`tables = []` means every table except `exclude_tables`, whose default already holds `sqlite_sequence`, `_cf_KV`, `__drizzle_migrations`, and `_smugglr_migrations`. Matching on `exclude_tables` is exact, not glob. A `--table` name that does not exist exits 2 and lists the tables that do.

Push adds and updates. A row deleted locally stays on the target, because deletes do not replicate on any path in 0.5.0 (smugglr#311). Rows the target holds and local lacks are left alone; that is `pull`'s direction.

## 2. Cloud to Local

Pull a copy of the target's data into a local database.

### When to use

You need a local copy of another database for development, debugging, or analysis. The target is the source of truth. The runnable form is the same example as pattern 1 with the roles reversed: `backup.db` holds the data and `local.db` is the empty copy. The D1 variant waits on smugglr#429, #430, and #436.

### Config

`docs/examples/cli-sqlite-to-sqlite/config.example.toml`, as in pattern 1. Build the files the other way around: `../westwind/make.sh --empty ./local.db` and `../westwind/make.sh ./backup.db`.

### Commands

See what is different before pulling anything. `diff` names the bucket each row landed in and prints the first five primary keys per bucket; one table here, to keep the block short:

```
$ smugglr diff --table shippers

--- Differences ---

shippers
  +3 remote only
    Remote only: 019438ea-9036-7221-933c-951305c6e3c1, 019438ea-9407-710d-937e-7bb98998b123, 019438ea-97d8-7ad2-b922-440d57e02ef3
```

Dry-run, then pull:

```
$ smugglr pull --dry-run

--- Pull Summary ---
  employees: 9 rows
  order_details: 788 rows
  orders: 320 rows
  products: 20 rows
  customers: 40 rows
  shippers: 3 rows
  categories: 8 rows
  suppliers: 8 rows

  (dry run - no actual changes made)
```

```
$ smugglr pull

--- Pull Summary ---
  categories: 8 rows
  employees: 9 rows
  customers: 40 rows
  order_details: 788 rows
  suppliers: 8 rows
  orders: 320 rows
  products: 20 rows
  shippers: 3 rows
```

```
$ smugglr pull

--- Pull Summary ---
  No changes to pull
```

### Watch for

The local file must exist and carry the schema before the first pull. smugglr opens it read-write without creating it; a missing file ends the run with `Local database error: unable to open database file: ./local.db` and exit 1. Run your migrations first.

Pull adds and updates. It never removes: a row local holds and the target lacks stays where it is (smugglr#311). Content hashing means a second pull against an unchanged target moves nothing.

Through the plugin, a hosted backend's rate limit is not retried in 0.5.0. A 429 or 5xx is reported as a permanent error and ends the pull on the first such response (smugglr#432).

## 3. Bidirectional Sync

Keep two databases converged with a stated rule for the rows both sides changed.

### When to use

Both databases take writes. Local dev and a shared copy. Two machines that see the same target. You need changes flowing both ways and a deterministic answer when the same row changed on each side. The runnable form is the pattern 1 example; the D1 variant waits on smugglr#429, #430, and #436.

### Config

`docs/examples/cli-sqlite-to-sqlite/config.example.toml`, as in pattern 1. The two keys that matter are `timestamp_column = "updated_at"` and `conflict_resolution = "local_wins"`.

### Conflict strategies

Every row lands in one of six buckets by comparing `timestamp_column` and the content hash: `local_only`, `remote_only`, `local_newer`, `remote_newer`, `content_differs`, `identical`. Under every policy, `local_newer` rows push and `remote_newer` rows pull. The policy decides only `content_differs`: rows whose timestamps match while their content does not.

| Strategy | Behavior on `content_differs` |
|----------|-------------------------------|
| `local_wins` | The local row overwrites the remote one. Default. |
| `remote_wins` | The remote row overwrites the local one. |
| `newer_wins` | Nothing moves; the row cannot be ordered, so it is skipped with a warning on stderr. |
| `uuid_v7_wins` | Behaves as `newer_wins` in 0.5.0. No UUID is parsed (smugglr#431). |

### Commands

Starting from a converged pair, six orders were edited locally, one customer and one product on the target, each edit bumping `updated_at`:

```sh
sqlite3 local.db "UPDATE orders SET freight = freight + 5, updated_at = updated_at + 60 WHERE ship_city = 'Dragonstone'"
sqlite3 backup.db "UPDATE customers SET contact = contact || ' (remote)', updated_at = updated_at + 60 WHERE code = 'ARBOR'"
sqlite3 backup.db "UPDATE products SET unit_price = unit_price + 2, updated_at = updated_at + 120 WHERE name = (SELECT name FROM products ORDER BY name LIMIT 1)"
```

```
$ smugglr sync --dry-run

--- Sync Summary ---
  orders: 6 pushed, 0 pulled
  products: 0 pushed, 1 pulled
  customers: 0 pushed, 1 pulled

  (dry run - no actual changes made)
```

```
$ smugglr sync

--- Sync Summary ---
  customers: 0 pushed, 1 pulled
  orders: 6 pushed, 0 pulled
  products: 0 pushed, 1 pulled
```

```
$ smugglr sync

--- Sync Summary ---
  No changes to sync
```

The product row was `remote_newer`, so it pulled under `local_wins`. The policy never saw it.

### Watch for

A `content_differs` row under `newer_wins` or `uuid_v7_wins` does not fail the run. It is skipped, both sides keep their version, the exit code is 0, and stderr carries one warning per table. Captured after editing the same supplier on both sides without touching `updated_at`, with `conflict_resolution = "newer_wins"`:

```
 WARN 1 row(s) in 'suppliers' have different content but missing or incomparable timestamps (skipped under newer_wins). Use local_wins or remote_wins to resolve.
```

Check stderr, not the exit code, for skipped rows.

`sync` is a push followed by a pull, per table, and it is not atomic. An interrupted run leaves one direction done and the other not; the next run picks up the rest, because applying a row twice is a no-op. Deletes do not replicate in either direction (smugglr#311); model a delete as a `deleted_at` column, which rides the upsert path and converges.

## 4. Background Sync

Run the watch daemon: a `sync` on an interval, in one process.

### When to use

You want the sync to happen without running commands. A development machine that follows a shared copy. A local database that mirrors another every thirty seconds. The runnable form is the pattern 1 example; the D1 variant waits on smugglr#429, #430, and #436.

### Config

`docs/examples/cli-sqlite-to-sqlite/config.example.toml`, as in pattern 1. There is no `[watch]` section. The interval is a flag, `--interval` (`-i`), default 30 seconds; a `[watch]` block in `config.toml` is ignored.

### Commands

In text mode `watch` writes nothing to stdout. Everything it says is on stderr. ```

To run it in the background, put the whole stream in a file: `smugglr watch >> smugglr.log 2>&1 &`.

### Watch for

Every tick is a full content-hash comparison of every configured table, the same work as one `smugglr sync`. After each successful tick the daemon writes `last_sync = "<timestamp>"` under `[sync]` in `config.toml`; it is informational and gates nothing, but it does mean the daemon edits your config file. On large tables a short interval is sustained load on the target; start at 30 seconds.

The daemon takes a PID lock, `.smugglr.pid`, beside the config file. A second daemon started on the same config refuses. It stops on SIGINT (Ctrl-C or `kill -INT`), finishing the current tick first. SIGTERM ends the process without the shutdown line and leaves the PID file behind; remove it before the next start.

An error classed as transient (the exit-3 family) is logged and the next tick retries. Any other error ends the daemon with that error's exit code, and in JSON mode the last line on stdout is a `"status":"error"` record. A locked or missing local file is fatal. In 0.5.0 nothing that comes back through the `smugglr-http-sql` plugin is classed as transient (smugglr#432), so against a hosted backend a 5xx ends the daemon rather than being retried on the next tick.

## 5. Multi-Machine (LAN)

Keep databases on machines that share a subnet converged over UDP multicast.

### When to use

Several machines on one LAN, or one virtual subnet through Tailscale, WireGuard, or ZeroTier, need the same rows. No relay, no server, no coordinator. Every node runs the identical loop: it multicasts a `primary_key -> content_hash` digest of its tables each interval, requests the rows it lacks, and applies what arrives idempotently. The runnable form is `docs/examples/cli-lan-broadcast`.

### Config

`docs/examples/cli-lan-broadcast/config.example.toml`, comments removed. Same `secret` and same `port` on every machine; paths need not match:

```toml
local_db = "./node.db"

[sync]
tables = []
timestamp_column = "updated_at"
exclude_columns = ["*_embedding", "vector"]

[broadcast]
secret = "REPLACE_WITH_OUTPUT_OF_openssl_rand_-hex_32"
port = 31337
interval_secs = 5
conflict_resolution = "newer_wins"
ordering_columns = ["updated_at"]
```

### Generate the shared key

```
$ openssl rand -hex 32
4e2a90071fefca644af45b2f563d914f272a1fa052cb96b268944246659b06b2
```

Paste one key into `secret` on every machine and distribute it out of band. With the key set, every datagram is XChaCha20-Poly1305 with a fresh nonce, and a node holding a different key sees ciphertext it cannot open. The key is membership. Leave `secret` out and the node still runs, in the clear, accepting any well-formed datagram on the subnet; it warns once at start.

### Commands

`broadcast` writes nothing to stdout in text mode; everything is on stderr. From the example README, captured from a test node with its own port, interval, and `instance_id` (timestamps and ANSI color stripped):

```
$ smugglr broadcast
 INFO Acquired PID lock: .smugglr-broadcast.pid (PID 30382)
 INFO Starting masterless multicast sync (group 239.255.43.21, port 31999, interval 2s, instance peer-d, dry_run false)
 INFO Opening local database: d.db
 INFO Heartbeat #1: multicast 1 digest datagram(s)
 INFO Heartbeat #2: multicast 1 digest datagram(s)
```

`--dry-run` advertises and applies nothing. `--once` sends one heartbeat, waits briefly for answers, and exits. `-v` shows every table read and every datagram handled.

### Watch for

UDP loses datagrams, and that is safe. Applying a row twice is a no-op, and the next heartbeat re-reconciles whatever a lost packet skipped. A late joiner that starts empty hears the next digest and converges with no special step.

Multicast does not cross routers or VLANs. Machines on different networks need a tunnel that puts them on one virtual subnet. UDP on the chosen port must be open on every machine; on macOS the application firewall silently drops inbound multicast for a binary it has not been told about, and the node hears nothing and logs nothing about it.

Conflict policy is apply-side and per node, and it is not negotiated on the wire. `remote_wins`, the default, is last-received-wins, so two nodes that receive two writes in different orders can hold different rows for that key. `newer_wins` takes the row whose `ordering_columns` maximum is greater and is the only policy that converges under concurrent edits; every node must set it. Deletes do not replicate (smugglr#311); a `deleted_at` column rides the upsert path and converges.

`exclude_columns` keeps the named columns out of the content hash, so an edit confined to them does not churn the mesh. In 0.5.0 those columns still ride the wire when a peer requests the row (smugglr#322). It is a hashing rule, not a privacy rule.

Two nodes on one host, for a first test, need two things the defaults do not give: a distinct `[broadcast] instance_id` in each config, because a node drops every datagram carrying its own id and the id defaults to the hostname, and a separate working directory for each, because each writes `.smugglr-broadcast.pid` where it starts.

## 6. Cross-Network

Stash and retrieve through an S3-compatible relay for machines that cannot see each other.

### When to use

Two machines on different networks, no shared LAN, no tunnel. The relay is a SQLite file in an object store (S3, R2, MinIO, or a `file://` path on a shared filesystem). One machine stashes, the other retrieves. The runnable form is `docs/examples/cli-stash-file-relay`, which plays both roles on one machine through a `file://` URL, so the whole workflow runs with no bucket and no credentials.

### Config

`docs/examples/cli-stash-file-relay/config.example.toml`, comments removed:

```toml
local_db = "./machine-a.db"

[stash]
url = "file:///tmp/smugglr-relay/relay.sqlite"

[sync]
timestamp_column = "updated_at"
conflict_resolution = "newer_wins"
```

Machine B's config differs only in `local_db`. For S3 or R2, replace `url` with `s3://bucket/path/relay.sqlite` and add `access_key_id`, `secret_access_key`, `region` (default `us-east-1`), and, for R2 or MinIO, `endpoint`. The key names a file, not a prefix. In CI, put the two keys in the environment with the `${VAR}` form the `cli-d1-sync` example uses for its token; an unset variable exits 2.

Setup, from the example README:

```sh
mkdir -p /tmp/smugglr-relay
../westwind/make.sh ./machine-a.db
../westwind/make.sh --empty ./machine-b.db
cp config.example.toml config-a.toml
sed 's/machine-a.db/machine-b.db/' config.example.toml > config-b.toml
```

### Commands

Machine A stashes. On the first run the relay does not exist, so smugglr creates it from A's schema, diffs A against it, and uploads it:

```
$ smugglr -c config-a.toml stash

--- Stash Summary ---
  categories: 8 rows
  customers: 40 rows
  employees: 9 rows
  order_details: 788 rows
  orders: 320 rows
  products: 20 rows
  shippers: 3 rows
  suppliers: 8 rows
```

Machine B retrieves. smugglr downloads the relay, diffs it against B, and applies the rows B lacks:

```
$ smugglr -c config-b.toml retrieve

--- Retrieve Summary ---
  categories: 8 rows
  customers: 40 rows
  employees: 9 rows
  order_details: 788 rows
  orders: 320 rows
  products: 20 rows
  shippers: 3 rows
  suppliers: 8 rows
```

```
$ smugglr -c config-b.toml retrieve

--- Retrieve Summary ---
  No changes to retrieve
```

Both commands take `--dry-run` and `--table`.

### Watch for

The relay is a SQLite file the diff engine syncs row by row, in both commands. `stash` downloads it, upserts local rows into it, and uploads it back; `retrieve` downloads it and upserts its rows into the local database. The local file is never replaced wholesale, and for two-way exchange both machines stash and retrieve, with `conflict_resolution` settling the rows both changed.

On S3 the upload is conditional on the ETag read at download, so two machines stashing at once cannot overwrite each other: the loser exits 4 (`conflict`) and runs again. On `file://` there is no ETag, the put is unconditional, and smugglr warns once. Point machines that write concurrently at separate `file://` relays.

Two limits before pointing this at a bucket. `exclude_columns` is not applied on this path in 0.5.0, so a column excluded from the hash still reaches the relay (smugglr#322). And the relay's schema is copied from the first machine to stash, so every machine needs the same tables. Deletes do not replicate (smugglr#311).

## 7. Disaster Recovery

Snapshot the local file before a risky operation. Restore when it goes wrong.

### When to use

Before a migration, a bulk update, a schema change, or anything where "oops" means data loss. A snapshot is a copy of the local database file stored under `snapshots/` on the relay. Restore replaces the local file with a snapshot. Both act on the local file only, never on a hosted target.

### Config

The `[stash]` relay from `docs/examples/cli-stash-file-relay/config.example.toml`; the `[sync]` section is not needed:

```toml
local_db = "./machine-a.db"

[stash]
url = "file:///tmp/smugglr-relay/relay.sqlite"
```

Snapshots go to `snapshots/` beside the relay file, on S3 as well as `file://`.

### Commands

Take a snapshot. Captured against a fresh Westwind build; the ledger table counts as one of the nine:

```
$ smugglr snapshot

--- Snapshot ---
  Timestamp: 2026-08-29T02:24:12.054Z-f2cd230b
  Size: 417792 bytes
  _smugglr_migrations: 8 rows
  categories: 8 rows
  customers: 40 rows
  employees: 9 rows
  order_details: 788 rows
  orders: 320 rows
  products: 20 rows
  shippers: 3 rows
  suppliers: 8 rows
```

Do the risky thing. It goes wrong (here, six orders deleted). List the snapshots:

```
$ smugglr snapshots

--- Snapshots ---
  2026-08-29T02:24:12.054Z-f2cd230b (417792 bytes, 9 tables, 1204 rows)

  1 snapshot(s) available
```

Restore is a whole-file swap, not a row merge. smugglr downloads the snapshot, runs SQLite's integrity check on it, and moves it over the local file. The report lists each table's row count in the restored file, not a diff against the current state. Dry-run, then restore:

```
$ smugglr restore 2026-08-29T02:24:12.054Z-f2cd230b --dry-run

--- Restore ---
  Restored snapshot: 2026-08-29T02:24:12.054Z-f2cd230b
  Size: 417792 bytes
  _smugglr_migrations: 8 rows
  categories: 8 rows
  customers: 40 rows
  employees: 9 rows
  order_details: 788 rows
  orders: 320 rows
  products: 20 rows
  shippers: 3 rows
  suppliers: 8 rows

  (dry run - no changes applied)
```

```
$ smugglr restore 2026-08-29T02:24:12.054Z-f2cd230b

--- Restore ---
  Restored snapshot: 2026-08-29T02:24:12.054Z-f2cd230b
  Size: 417792 bytes
  _smugglr_migrations: 8 rows
  categories: 8 rows
  customers: 40 rows
  employees: 9 rows
  order_details: 788 rows
  orders: 320 rows
  products: 20 rows
  shippers: 3 rows
  suppliers: 8 rows
```

The six orders are back. Same block, same counts.

### Watch for

Pass the name as `snapshots` prints it, suffix included, or any later timestamp: `restore` takes the latest snapshot at or before the argument. The bare timestamp without its suffix sorts before the snapshot and fails with `No snapshot found at or before`.

`snapshot` reads the database file as it is on disk. A database in WAL mode with an uncheckpointed WAL loses those pages from the snapshot (smugglr#433); run `PRAGMA wal_checkpoint(TRUNCATE)` first. The copy carries schema and data together, and `restore` puts both back, so a schema change made after the snapshot is undone with it.

Restore overwrites the local file. Dry-run first, and take a snapshot of the broken state before restoring the good one; then you hold both. Snapshots on S3 or R2 are objects and cost storage; a bucket lifecycle rule on the `snapshots/` prefix expires the old ones.

## 8. CI/CD Integration

Run a push as a deploy step, with the exit code driving the pipeline.

### When to use

Your pipeline seeds a hosted database from a checked-in SQLite file, or checks that the two agree before shipping. Exit codes and JSON are the interface. The runnable form is `docs/examples/cli-http-sql-turso`, the shape every hosted backend uses; the D1 variant waits on smugglr#429, #430, and #436.

### Config

`docs/examples/cli-http-sql-turso/config.example.toml`, comments removed:

```toml
local_db = "./local.db"

[target]
type = "plugin"
name = "http-sql"

[target.config]
profile = "turso"
url = "https://my-db.turso.io"
auth_token = "${TURSO_TOKEN}"

[sync]
tables = []
timestamp_column = "updated_at"
conflict_resolution = "local_wins"
```

`name` is the plugin binary, `smugglr-http-sql`, resolved from `~/.smugglr/plugins/` or `$PATH`. `profile` picks the backend: `d1`, `turso`, `rqlite`, `datasette`, `sqlite-cloud`, `starbasedb`, `generic`, `http-sql`. `${TURSO_TOKEN}` is expanded at load; unset, it exits 2.

### GitHub Actions example

`--output json` is a global flag and goes before the subcommand.

```yaml
# .github/workflows/deploy.yml
name: Deploy with DB sync
on:
  push:
    branches: [main]

jobs:
  sync:
    runs-on: ubuntu-latest
    env:
      TURSO_TOKEN: ${{ secrets.TURSO_TOKEN }}
    steps:
      - uses: actions/checkout@v4

      - name: Install smugglr and the http-sql plugin
        run: cargo install smugglr smugglr-http-sql

      - name: Dry-run
        id: dryrun
        run: |
          smugglr --output json push --dry-run > dryrun.json
          echo "rows=$(jq '.total_rows_to_push' dryrun.json)" >> "$GITHUB_OUTPUT"

      - name: Push
        if: steps.dryrun.outputs.rows != '0'
        run: |
          code=0
          smugglr --output json push > result.json || code=$?
          if [ "$code" -ne 0 ]; then
            echo "::error::smugglr push failed with exit code $code"
            cat result.json
            exit "$code"
          fi
          echo "Pushed $(jq '[.tables[].rows_pushed] | add // 0' result.json) rows"
```

### Exit codes in CI

Codes map from the error, not from the command.

| Code | Meaning | CI action |
|------|---------|-----------|
| 0 | Success | Continue. |
| 1 | General error | Fail. Plugin and adapter failures land here; there is no plugin-specific code. |
| 2 | Configuration error | Fail. Bad TOML, an unset `${VAR}`, or a `--table` that does not exist. Fix the config. |
| 3 | Connection error | Retry the step. |
| 4 | Conflict | Fail. A relay ETag mismatch from `stash`, or a duplicate primary key. |
| 5 | Target not found | Fail. A database file, relay, or table the target lacks, or a rejected request. |

### Shell retry for exit 3

```bash
#!/bin/bash
MAX_RETRIES=3
RETRY_DELAY=5

for i in $(seq 1 $MAX_RETRIES); do
  smugglr --output json push > result.json
  EXIT_CODE=$?

  if [ $EXIT_CODE -eq 0 ]; then
    echo "Push succeeded on attempt $i"
    exit 0
  elif [ $EXIT_CODE -eq 3 ]; then
    echo "Connection error on attempt $i. Retrying in ${RETRY_DELAY}s."
    sleep $RETRY_DELAY
    RETRY_DELAY=$((RETRY_DELAY * 2))
  else
    echo "Exit code $EXIT_CODE. Aborting."
    cat result.json
    exit $EXIT_CODE
  fi
done

echo "Failed after $MAX_RETRIES attempts."
exit 1
```

### Watch for

Use `--output json` in CI and parse stdout; tracing goes to stderr. Keep secrets in the environment through `${VAR}` and never in the committed file. Skip the push when the dry-run reports zero rows.

Exit 3 is the only code worth retrying, and in 0.5.0 it does not come back through the plugin: a 429 or 5xx from the backend is reported as a plugin error, exit 1, and the built-in retry with backoff never runs (smugglr#432). Until that lands, the loop above aborts on a rate limit rather than waiting it out.

A snapshot step is not a rollback for this pattern. `snapshot` copies the local file, which in CI is the checked-in seed; it does not capture the hosted target.

## 9. Agent Automation

JSON on stdout and typed exit codes, for an agent that calls smugglr and decides what to do next.

### When to use

An agent (Claude Code, a custom loop, a legion daemon) syncs data as part of an autonomous workflow. It runs a command, parses one JSON object, reads the exit code, and continues, retries, or escalates. No human in the loop. The runnable form is the pattern 1 example, where the JSON blocks below were captured; the D1 variant waits on smugglr#429, #430, and #436.

### Config

`docs/examples/cli-sqlite-to-sqlite/config.example.toml`, as in pattern 1.

### Agent decision logic

Dry-run first and read `total_rows_to_push`; zero means skip. Push, and branch on the exit code: 0 is done, 3 is retry with backoff, anything else is abort with the `error` string. On 0, sum `rows_pushed` and compare it with the dry-run's `total_rows_to_push`; a shortfall means rows were skipped under `newer_wins` or `uuid_v7_wins` (pattern 3), which is reported as a warning on stderr and never as a non-zero exit, so it is the one condition an agent must infer.

```python
import json
import subprocess
import time


def smugglr_push(config_path="config.toml", max_retries=3):
    """Dry-run, then push. Returns a dict with an `action` for the caller."""
    base = ["smugglr", "--output", "json", "--config", config_path]

    dry = subprocess.run(base + ["push", "--dry-run"], capture_output=True, text=True)
    if dry.returncode != 0:
        result = json.loads(dry.stdout) if dry.stdout else {}
        reason = result.get("error", "unknown error")
        if dry.returncode == 3:
            return {"action": "retry", "reason": reason}
        return {"action": "abort", "reason": reason, "exit_code": dry.returncode}

    expected = json.loads(dry.stdout)["total_rows_to_push"]
    if expected == 0:
        return {"action": "skip", "reason": "no changes detected"}

    for attempt in range(1, max_retries + 1):
        push = subprocess.run(base + ["push"], capture_output=True, text=True)

        if push.returncode == 0:
            result = json.loads(push.stdout)
            pushed = sum(t.get("rows_pushed", 0) for t in result["tables"])
            if pushed < expected:
                # Skipped conflicts exit 0; the warning is on push.stderr.
                return {
                    "action": "escalate",
                    "reason": "fewer rows pushed than the dry-run predicted",
                    "stderr": push.stderr,
                    "result": result,
                }
            return {"action": "ok", "result": result}

        error = json.loads(push.stdout) if push.stdout else {}
        if push.returncode == 3 and attempt < max_retries:
            time.sleep(2 ** attempt)
            continue
        return {"action": "abort", "reason": error.get("error", "unknown"), "exit_code": push.returncode}

    return {"action": "abort", "reason": f"failed after {max_retries} retries"}
```

### Watch for

Parse stdout, never stderr. In `--output json` mode stdout is one valid object, on success and on error, and stderr is empty except for the skipped-conflict warning described in pattern 3.

Retryability is the exit code, not a field. Exit 3 is retry; 2 is fix the config; 4 is a human decision (a relay ETag conflict from `stash`, or a duplicate primary key); 1 and 5 are abort. In 0.5.0 a plugin failure of any kind, including a backend 429 or 5xx, is exit 1 (smugglr#432), so an agent driving a hosted backend sees exit 1 where it would expect 3.

For a long-running loop, `smugglr --output json watch` (pattern 4) prints one object per tick on stdout, and the agent reads the stream instead of polling.
